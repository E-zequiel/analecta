# Wayland Tray Focus: Architecture and Constraints

**Status:** Implemented  
**Date:** 2026-06-04

---

## Problem

Clicking "Add URL from clipboard" in the system tray should bring the Analecta window to the foreground with keyboard focus and pre-fill the URL input from the clipboard. On Wayland this fails in specific scenarios due to two independent protocol-level restrictions.

---

## Wayland Restrictions

### Restriction 1 — Focus activation requires a user-gesture serial

`BrowserWindow.focus()` in Electron uses the `xdg_activation_v1` protocol. A valid activation token must be generated by a surface that **currently holds keyboard focus**, in response to a Wayland input event carrying a compositor-issued serial. This token is then passed to the target surface to claim focus.

The tray menu is implemented via D-Bus (`StatusNotifierItem`). A D-Bus method call carries no Wayland input serial, so Electron cannot generate a valid activation token from it. The compositor silently ignores `win.focus()` calls made in this context.

**Observed failure pattern:**

| Scenario | Result |
|---|---|
| Another app held focus when the user left the workspace | ✅ Focus transfer succeeds — the compositor has a legitimate focus holder to transfer from |
| Analecta held focus when the user left the workspace | ❌ Fails — Analecta is already the designated active window for that workspace; the self-referential request has no valid token source |
| Analecta is the only app in the workspace | ❌ Always fails — no focus holder exists to donate a token |

Tested on **cosmic-comp 1.0.15** (Pop!_OS 24.04 LTS, Wayland native).

### Restriction 2 — Clipboard access requires keyboard focus

`clipboard.readText()` uses `wl_data_device` / `zwp_primary_selection`. These protocols only return clipboard content to the process that currently holds keyboard focus. Without focus, `clipboard.readText()` returns an empty string with no error. This restriction is enforced at the Wayland protocol level and is independent of the compositor implementation.

---

## Solution

### Notification portal as activation source

When a user clicks an action on a desktop notification, that click is a genuine Wayland input event. The notification daemon emits `ActionInvoked` over D-Bus carrying an `activation-token` that the compositor considers valid.

Electron 42+ (PR [#50568](https://github.com/electron/electron/pull/50568), merged April 2026, backported to `42-x-y`) recovers this token from `libnotify` via `dlsym` and injects it using `base::nix::SetActivationToken()`. The subsequent `win.focus()` call then carries a valid token and succeeds.

**Implementation** (`electron/main/tray.ts`):

```
Tray click → silent persistent notification
           → user clicks notification
           → libnotify emits ActionInvoked with activation token
           → Electron injects token → win.focus() succeeds
           → webContents.send('tray-paste-url')
```

The notification uses `timeoutType: 'never'` so it remains visible until the user acts, distinguishing it from informational auto-dismiss notifications (e.g. "New entry saved.").

A fallback path is retained for environments where `Notification.isSupported()` returns false.

### Serialized clipboard read in the renderer

Since Restriction 2 depends on focus being established before `clipboard.readText()` is called, the renderer defers the clipboard read until focus is confirmed (`frontend/src/lib/components/Sidebar.svelte`):

```
tray-paste-url received
  → urlInputActive = true  (modal renders)
  → await tick()
  → document.hasFocus() ?
      yes → read clipboard → fill input → focus input
      no  → register window 'focus' listener
              → on focus: read clipboard → fill input → focus input
```

The `window focus` listener covers the residual case where focus arrives asynchronously (e.g. workspace switch latency). It is guarded with `get(urlInputActive)` to no-op if the modal is closed before focus arrives.

## Alternatives Considered

| Approach | Outcome |
|---|---|
| `win.focus()` directly from tray click | Fundamentally broken — no valid xdg-activation token possible from D-Bus |
| `app.focus({ steal: true })` | No-op in GNOME and cosmic-comp without a valid serial |
| `win.moveTop()` before `win.focus()` | No effect on cosmic-comp in tested scenarios |
| `ProvideXdgActivationToken` (SNI extension) | KDE/KWin only; not implemented in GNOME Shell or cosmic-comp |
| XDG Portal `org.freedesktop.portal.Activation` | Does not exist as a standalone portal; mechanism is embedded in the notification portal flow |
| `wlr-foreign-toplevel-management` | Protocol is available in cosmic-comp but is reserved for shell-privileged clients, not user applications |

---

## Dependencies and Constraints

- **Electron 42+** required for the activation token extraction from `libnotify` (PR #50568).
- **`libnotify`** must be installed on the user's system. The symbol `notify_notification_get_activation_token` is resolved dynamically at runtime; absence of `libnotify` degrades gracefully to the fallback path.
- The notification portal path is compositor-agnostic: the token is valid under GNOME Shell, cosmic-comp, KDE Plasma, and any compositor implementing `xdg_activation_v1`.
